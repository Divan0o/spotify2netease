# 风格审查与查询改路

## 为什么可能先返回歌单或同名歌曲

已观测到泛“推荐 N 首某风格”返回5个playlist、0首track；结合工具声明的混合实体返回能力，推断推荐意图可能触发歌单路由，不能声称知道其服务端实现。接口每次最多5个实体，没有硬 `type=track`、limit或可靠genre过滤参数；要求10首不意味着一次能返回10首。只加track可能改善实体类型，仍可能仅按歌名匹配风格词。不要把MUSIC类型、Premium泛化提示或查询命中当风格认证。

2026-09-06 的 Deep House 实测中，泛推荐、艺人加风格、一次拼接5首作品都返回了歌单；“搜索deep house风格的歌曲，结果类型为单曲（track），不要歌单”返回的5首全部是曲名为 Deep House 的命中。随后10次单首 `艺人 - 曲名` 查询均返回了目标单曲，部分响应也含专辑或歌单。

同日按用户要求追加10次 `{track}` 对照：`deep house {track}` 两次均返回5首单曲，但4首标题为 Deep House；`Kerri Chandler {track}` 两次均为5首身份匹配的单曲，不加后缀则为3首单曲、1个艺人、1个歌单。前置 `{track}`、裸 `track`、完整推荐句后加 `{track}` 均为5个歌单。采用短查询末尾的字面量 `{track}`，保留大小写和花括号；这是当前插件的实测提示行为，不是已公开或有保证的 API 参数，也不能保证曲风。详细对照见[验证记录](../tests/VALIDATION.md)。

## 分开核验身份和风格

- 接收插件返回的track实体，保留完整creators、artist URI、专辑、版本、时长与原链接。先复用同风格历史未推荐候选，再使用具体作品线索。冷启动可用可靠作品知识提出少量 `艺人 - 曲名` 检索假设；假设不是已确认身份或最终推荐，不能据此编造 Spotify 实体。每首必须来自真实Spotify响应或其可追溯缓存，不能凭记忆、网页或自造实体补歌。
- 明确用户风格的语义边界。准确同义词可用，邻近流派、流行混合曲与衍生版本不是自动等价。
- 每首保存 `accepted / uncertain / rejected`、具体 basis、证据数组；证据必须针对该曲或发行，不能只有艺人流派背景、标题、时长或网易云匹配。
- 可使用明确可靠的作品知识，但须标记 `kind: knowledge, certainty: known`，不能把猜测写成 known。冷门、模糊或记忆不确定的事实应联网核验。
- 外部核验只围绕 Spotify 已返回的候选。优先该曲发行方、唱片厂牌、创作者的发行介绍，必要时可靠音乐媒体；保存真实支持该曲风格的 URL 和 claim。网页未给出内容不能填造证据；不能从网页发现另一首歌后直接入选。
- 有证据但只属于邻近风格，记 uncertain 或 rejected，不能为满额降门槛。脚本检查的是证据结构，不会替代音乐判断，也不能证明输入的依据真实。

## 查询策略

先 `plan`，按 `select → review → reuse → discover` 的优先级行动。缓存复用不占Spotify调用、不预留推荐历史；已accepted的同录音证据可沿用，未审候选仍须assess。缓存不代表当前可播放或满足“最新发行”，有实时要求才定向刷新。保持全局录音去重、原作者软上限和网易云版本匹配，不以省查询为由降门槛。

### 首轮检索规则

1. **有可用缓存先复用**；不足时再选检索线索。按用户要求保留 `风格 {track}` 为正常发现入口，冷启动默认使用；有已确认的同风格艺人线索也可用 `艺人名 {track}`，有用户指定作品时直接查该作品。允许标题匹配，不要求先有作品级证据才执行风格检索。不要固定重复推荐同一套经典曲目。
2. **每次请求只有一个主体**：风格检索用 `deep house {track}`，艺人检索用 `Kerri Chandler {track}`，末尾是空格加字面量 `{track}`；定位具体录音用 `Kerri Chandler - Rain`，需要时带版本名。后缀不要前置，不改成裸 `track`，不拼入完整推荐句，也不一次列出多个主体。`language` 按用户语言设置，名称保留原文。标题等于风格词的单曲照常入池、去重和审查；`title_hits` 只是统计，不是拒绝或换路条件。标题匹配本身也不自动证明该录音属于目标风格。
3. **遵守工具契约**：以上是用户要求优化的检索流程；调用时仍须使用当前工具允许的请求透传或上下文消解方式。不能声称用户点名了模型提出的线索。若工具契约使该检索无法执行，应报告实际限制，不退回已知会返回歌单的泛推荐来假装完成，也不编造 `type`、`limit` 或分页参数。后缀只在 `prompt` 内使用。
4. **完整记录、只审单曲**：每次响应都交给 `ingest`，包括全为歌单的失败响应；已知 artist URI 时附 `--artist-uri` 做身份校验。只接受实际 `spotify:track:` 单曲实体进入推荐池，歌单和专辑不占推荐数量。混合响应和标题匹配的单曲均正常审查；零单曲、全部重复或经作品级审查无合格项时换艺人或具体作品线索，不重复已无产出的查询。
5. **每轮审完再扩展**：每轮默认1次、最多并行2次独立查询；得到响应后立即 `ingest → plan → assess → select`，有剩余缺额才继续下一轮。艺人后缀查询返回的作品也需逐曲评估，不能以艺人身份代替作品级曲风证据。后缀查询无有效产出时改查具体作品，不重复原查询碰运气；保留额外候选供审查或缓存，继续全局录音去重。

不要把艺人多样性上限误变成搜索配额。按剩余缺额和具体作品证据选择下一首，不预设每位艺人搜一次或各取两首。artist-uri用于ingest校验而非伪造搜索参数。没有身份上下文的常见同名艺人优先暂缓；错误实体不值得继续扩展。

10首全无缓存时，在每次最多5实体的接口下，2次只是全为合格不重复单曲时的理论下限，不承诺2次完成。并行降低等待但不减少调用次数；分别统计新Spotify调用、缓存复用和网易云搜索。不要为了达到某个调用数字提前停止，也不要满额后补做验证性搜索。

- **退出无效分支，不结束整个任务**：风格或艺人后缀查询经审查没有合格产出时，改查另一艺人或具体作品；具体作品也无产出时换有依据的下一条线索。允许 `风格 {track}`，但不重复泛推荐句或多主体拼接的已知低效路线。相似作品返回其他曲风时不沿其合作艺人继续扩散。
- **每轮处理完再扩池**：优先处理已 accepted 且去重通过的候选；下一批待审只保留缺额+2（最多12首）的工作窗口，其余仍存库，不自动丢弃。每轮默认1次、至多2个独立搜索；已有够用候选时先完成审查和select，不再同时发散新分支。已满N不做“再找几个更好”的额外探索。
- **证据检索按收益安排**：明确误风格/身份错配直接 rejected，信息不足标 uncertain 暂存，不统统联网追查。先查有望入选的具体作品；一次权威来源能支持同发行多首时共用，但不能由一首推断全专辑。一份可靠且对应版本的作品级证据足够时不重复跨站验证；冲突时才加查。一个候选定向核验后仍无依据，暂存并换候选，不无限深挖。以后有新证据可重审，不宣称永久不合格。
- **以合格产出而非实体数量换路**：`queries` 记录单曲、新URI、身份错配和合格数量。只返回新URI但没有可核验作品，不算有效进展。artist/相似查询不因出现新名字就可靠；优先本流派作品级证据更扎实的种子。总流程仍持续到N，分支退出不是恢复“连续两次无新增就停止”的总停止规则。
- **保留有用记忆**：plan同时给出缓存单曲、艺人线索和历史无单曲／全部否决的查询。reuse只导入未推荐且无冲突的同风格候选，保留来源批次，不复制旧匹配或歌单状态。`uncertain`候选不自动搬到新批重审，避免反复追查；有新证据时再针对原候选处理。无评估不等于不合格，已推荐不等于仅曾被搜索到。

默认主艺人软上限为 `ceil(N/5)`（10 首为 2），按 Spotify artist URI 优先计数。狭窄曲风、用户要求单艺人等可通过 `--diversity-reason` 记录具体理由覆盖；不能随意用“凑够数量”覆盖。

## 录音去重

同 URI 或同 ISRC 排除；完整艺人集合和规范化歌名相同且时长相差 ≤500ms，按同录音排除，即使专辑不同。保留 Remix、Edit、Live 等版本词；不同版本仍单独评估风格。旧历史缺时长、或同名艺人和歌名但时长不同，记 possible，只有具备真实不同版本证据才在 select 的 distinct_reasons 中放行。不同发行 URI 本身不是不同录音证据。
